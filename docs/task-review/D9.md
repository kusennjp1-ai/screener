# D9 implementation and acceptance

## Implementation

The radar uses the unchanged canonical `entryPlan` and reference `radarGeometry`: only qualified rows with a valid pivot and finite RS produce a point. No generated points, replacement values, selection thresholds or fixture prices were added. The 207 observations are the immutable 2026-09-29 fixture with SHA-256 `3841eaefff22a87c61a2ba5be42bb3c2e1eb254c44008827eb2b152798c52452`.

The initial SVG version exceeded the 50 ms budget. Independent cold CPU/timeline recordings identified initial React DOM setup and SVG layout as the large costs, rather than financial calculations. The production renderer now draws the same points on Canvas, with an immutable HTML label frame and an SVG selection overlay. A minimal component lifecycle preserves the canvas during hover and selection, and observes theme, CSS size and pixel-density changes. The palette remains centralized. Topmost hit testing follows the original painter's order; unavailable charts remain unselectable. The SVG overlay uses `preserveAspectRatio="none"` so a height-limited plot, Canvas and HTML labels use the same coordinate transform.

The draw loop records a count only after drawing its actual circles. The benchmark reads this completed-draw count in place of the old implementation-specific `circle > title` selector. Missing drawing cannot pass the count check. The original timing interval and 50 ms threshold are unchanged.

## 2026-10-02: integrated cold regression and observed-size rendering

The eighth integrated measurement exceeded the budget again: PC first frame 52.9 ms (synchronous render/layout 43.9 ms), mobile 48.3 ms (42.2 ms), with 207 actual points in every run. The earlier focused pass is retained as historical evidence; it does not supersede this integrated failure. Repeating an unchanged build until a favorable result occurs is not treated as a fix.

The cold profile attributed about 11 ms to layout inside `getBoundingClientRect`. The integrated P1 diagnostic also showed this read forcing 52–65 ms layouts during mount/resize. `7f2676f` removes the synchronous size read from the normal React commit: all points are still drawn synchronously at the known logical size and DPR, then the browser's pre-paint `ResizeObserver.contentRect` supplies the actual dimensions. Theme and DPR changes reuse those dimensions. Browsers without ResizeObserver retain the synchronous actual-size fallback.

The original React mount → synchronous draw/layout → next-frame timing boundary, cold first run, three-run requirement, 207-point fixture and 50 ms limit are unchanged. Both the formal Design gate and focused diagnostic now additionally require 207 final points and backing dimensions matching the real CSS box × DPR at that boundary. A separate fresh DPR2/non-proportional-size diagnostic checks the same completed sizing; it cannot replace any formal run. These checks prevent passing solely on a temporary logical-size drawing while required physical-resolution work occurs after the measured boundary.

The current targeted suite passes 15 tests, including no forced layout reads during normal mount/observer/theme/DPR handling, synchronous full drawing, actual-size alignment, duplicate/invalid observer notifications, and the no-ResizeObserver fallback. Targeted lint reports zero errors and the benchmark production build succeeds. New CI performance and physical-resolution results remain pending.
