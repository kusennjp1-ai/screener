# Same-UI, same-price source renewal

This is isolated local implementation. Publication remains **disabled** and the
renewal policy's reviewed-controller registry remains **empty**. No provider
collection, schedule, source trust entry, push, activation or deployment is
included. The original initially approved packed repair must finish separately;
this code does not renew its original observation clocks or authorize release.

## Independent proof boundary

`financial-source-renewal.mjs` defines closed request, pin, intent, candidate,
source-delta, transition and retained-chain contracts. They bind the exact live
predecessor financial receipt, activation origin, source lineage, full published
UI inventory/approval, consumer and financial-policy code, full current price
artifact/manifest/ledger/universe, exact source ZIP/certificate/base/cohort,
original acquisition journals, logical and physical candidate inventories, and
append-only audit history. A candidate or environment variable cannot supply
source/controller trust. All source certification and financial projection use
the existing strict validators and formulas.

The request selects the currently published Pages artifact as its price input,
not the older export artifact named by a previous financial receipt. The source
archive retains the original full cohort; publication applicability exclusions
do not authorize changing that cohort. A genuine later acquisition may bind a
new current-price base through the existing archive planner/merge mechanism.
Its old receipt/object/attempt/batch entries remain unchanged with their original
origin bindings. The unmodified statement projector still requires that new
acquisition base to agree with the full target price/date/universe.

`verify_statement_source_renewal.py` reopens both archives and projection receipt
inventories. Every original object, receipt, attempt and batch entry must remain
identical. Progress requires a new current receipt and capture identity, strictly
later original getter observation, successful original acquisition journal,
plan/cache bindings, and original transport/getter/attempt completion clocks.
Repeated real retrieval may return equal provider values. Wrapper changes,
evaluation clocks, cache reuse and journal-free seeded receipts are not progress.
Partial renewal is allowed: untouched receipts keep their original bytes/clocks.
Expired, conflicting or unavailable evidence never receives scalar fallback.

## Artifact-only certification

`.github/workflows/financial-source-renewal-certification.yml` is manual with
contents/actions **read** permissions. Its production commands are:

1. `controls`: validate the committed request and exact workflow context.
2. `prepare`: read the verified live predecessor and exact retained artifacts;
   run the existing source certification, native projector and compiler proofs.
3. `verify-source`: reopen original ZIPs and verify the journal-bound delta.
4. `verify-surfaces`: replay the native projection, financial-only comparison,
   consumer compatibility, full prices/universe and original release authority.
5. `verify-bounds`: measure the physical candidate with the actual Pages guard.
6. `seal`: repeat proofs and seal the exact candidate and complete retained TAR.

The compiler prepares financial data using the unchanged approved consumer.
For renewals only, baseline preparation restores the exact published candidate-
performance descriptor, report and observation archive before running the
unchanged strict comparator. An ordinary price carry records its first daily
catalog entry after exporting its report; a same-price renewal must not add that
entry retroactively to performance cohorts or freeze extra observations. The
published daily catalog and all financial/compiler outputs remain independently
verified. Original preview behavior and comparison tolerances are unchanged.
The producer copies HTML, JavaScript, service worker and other UI assets from
the authenticated predecessor, so emitted build variation cannot change the
published UI. It packs the result using the existing lossless transport. The
archive retains both new and previous source/certificate ZIPs, the complete
predecessor ZIP and extracted tree, original source histories, source delta,
preview evidence, source projection, target base, certification registry bytes,
certifier CI evidence, and all required inventories.

Verification requires retained originals and uses strict offline source restore;
missing archive material fails instead of silently downloading it. API evidence
remains read-only and is rechecked against exact immutable attempts. The source
certifier's own reviewed trust boundary is unchanged.

## Staged controller authority without a hash cycle

The earlier unpublished scaffold embedded a controller commit/tree in the policy
file contained by that same commit. That self-reference cannot be instantiated.
The completed contract separates three immutable stages:

- **A, certification:** committed request, exact certifier code/tree and successful
  main CI; candidate seals the raw registry bytes and exact certifier CI record.
- **B, reviewed controls:** the same executable controller code and committed
  request, successful A candidate pin, explicit bounded intent, and successful
  main CI. A later independent review names this immutable B commit/tree.
- **C, publication:** exact current main, successful CI, unchanged request/pin/
  intent bytes, and an append-only registry containing the one exact A/B review.
  The transition retains C's SHA/tree/CI and raw registry digest independently.

Executable code equivalence omits only the renewal registry policy file. Its
bytes are separately authenticated at A/B/C, all non-registry policy semantics
must remain identical, and prior registry entries must be preserved in order.
Only the publication-enabled flag and append-only exact reviews may differ.
There is no wildcard tree, source, artifact, request, intent, or successful-job
shortcut. The financial source trust file is authority metadata rather than a
consumer formula: UI-to-A preserves its original entries/code and allows only
appended exact reviewed requests; A-to-C must be identical. All original v1/v2
approval/capture policies and original source trust entries remain unchanged.
The captured UI predates the already-reviewed v2 activation-policy enablement;
that metadata file is excluded from consumer equivalence only. Its A bytes must
exactly equal the immutable original activation controller's policy, with the
original v2 approval and financial scope independently reverified. A/B/C full
controller equivalence still includes the file. No policy bytes or scope change.

The codec integration also introduces four acceptance-harness differences from
the real captured UI: `frontend/src/static/staticPublication.test.js`,
`frontend/tools/production-bootstrap-diagnostic.mjs`,
`frontend/tools/production-bootstrap-diagnostic.test.mjs`, and
`frontend/tools/publication-cli.test.mjs`. The consumer inventory and its original
capture digest remain unchanged. Only an exact before/after pair already present
in the independently reverified original v2 activation's `controller_changes`
may be normalized back to its capture blob for this comparison. Missing pairs,
later edits, reversion to a before blob, and every other consumer change fail.
All four remain in the complete, equal A/B/C controller inventories. Ordinary
activation origins receive no exception. The diagnostic affects Design acceptance,
so its initial review and original approval scope remain mandatory.

This branch adopts the exact separately reviewed initial-release PR77 baseline:
public main `5098a762f640d8d477594cbe337cf12baf5866a5`, tree
`d71ae65ce59f382e164bebcd6f5a270e379f983b`, equivalent to local controller
`1cf33e272dec97e67c972c8163815a6c873e451a`. Its original v2 scope and approval
already enumerate the four pairs. Those authority bytes are preserved; renewal
adds no original-v2 permission. Tests of the pairs use disposable fixture
identities with that unchanged finite scope. This static baseline adoption is
not live-origin evidence: actual renewal still requires the deployed initial
activation receipt and its independently reverified immutable certificate.

## Serial publisher and retained lineage

The existing serial publisher accepts only the explicit typed manual
`financial_source_renewal` dispatch matching all three committed controls. A
renewal is exclusive of Design, correction and UI-only modes. It requires the
exact current published predecessor artifact, current-main checkout/tree/CI,
exact successful certification attempt/steps/artifact, unexpired intent, and
independent source/controller review before selecting the candidate.

The real `select-release-source.mjs` plan/restore/compose/recheck path verifies
and restores that candidate. Compose preserves the exact UI, current full price
series/ledger/universe and prior financial audit; appends a content-addressed
transition and v2 financial receipt; then losslessly repacks. The renewal path
has its own narrowly allowed transition addition. The original v2 activation
transport addition scope is unchanged.

The final logical inventory, original encoded payload bytes, full physical
inventory, appended financial assets, publication generation/lineage/reference,
and actual uncompressed upload TAR are rechecked. The Pages file and TAR limits
remain 1,000,000,000 bytes; the independent 8 GiB retained-archive limit does not
increase them. Both existing final publisher rechecks reread exact current-main
CI/code/control/registry authority, original source proofs and live predecessor.
A concurrent predecessor change invalidates the prepared release. Explicit
intent removal, registry-only mutation, wrong attempts/hashes or a substituted
financial generation also invalidate it.

Publication metadata also records a bounded, content-addressed `financial_audit_files`
inventory. Every later carry restores the whole listed audit set, verifies its
bytes, and appends its new receipt/evaluation. The original active v1 activation
can seed the first inventory without changing its receipt. This fixes the prior
clean-restore behavior where a second ordinary carry could omit the activation
receipt while retaining current financial values. Already-lost historical files
are not fabricated or silently recovered; exact retained artifacts are required.

The v2 receipt retains an unchanged original v1 activation receipt and ordered
content-addressed transitions. Historical reading rechecks the original approval
and every saved immutable A/B/C authority; it does not require expired operational
artifacts or old intent files to remain current. A subsequent ordinary price
carry preserves renewed source assets and authority, and another renewal extends
the same origin. Current control removal does not block historical ordinary carry.

These are local synthetic source/market/API executions with real collector,
certifier, projector and publisher code. They establish no real provider refresh
or deployed original activation. Neither the small passing fixture nor the
unchanged 8 GiB archive allowance establishes full-universe renewal capacity.
Measured retained-original candidate inventories and the final physical Pages
TAR remain necessary. The original first-activation rehearsal stays separate.

Before any real renewal, obtain separately authorized genuine source receipts,
independently review their exact source-certifier tree/request, certify the

Changing `publication_enabled` alone cannot grant authority. Collection cadence,
provider-barrier handling, single-writer scheduling, retention preflight and
measured renewal latency remain separate work.
