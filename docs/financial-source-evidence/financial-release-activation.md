# Coordinated financial activation and dated carry

The mechanism is enabled, but activation remains held until an exact candidate
is pinned in `.github/financial-activation-candidate.json`. Neither a preview, a
successful source certificate, a pending hold, nor a boolean backup assertion
grants publication authority.
The existing `financial_correction` dispatch remains prepare-only.

## One tested artifact

A closed `.github/financial-release-request.json` binds the exact predecessor,
original source artifact and explicit certified-source/native-destination
selection. It contains no claimed current-main SHA. Design Acceptance reads the
actual checkout commit/tree and builds the coordinated v2 candidate offline.
Its comparison baseline uses the exact predecessor's evidence; its measured
current build is the corrected candidate directory. Those different financial
inputs are recorded honestly in the candidate receipt.

The existing route, screenshot, accessibility, CPU and size budgets measure that
directory. Only after both design checks succeed does the job hash and archive
the same bytes, together with the source/certificate/predecessor ZIPs, projection,
baseline and verification report. It does not rebuild after measurement. PR
runs use this same preparation path but cannot authorize publication.

The serial Research UI Release controller can select only the uniquely named
artifact from the exact
successful current-main Design attempt, and only with all existing exact-main
CI and Design jobs successful. It checks every required measuring/sealing step,
job/run SHA, time interval, artifact ID and ZIP digest. Captured UI commit/tree
remain explicit. All protected UI, exporter, projector, contract, workflow and
IBD-reference Git blobs must equal the approved controller checkout.

## Exact candidate handoff

The closed activation pin is a control record outside the protected source
prefixes. No compiler, evaluator, exporter, contract or workflow is excluded from
the protected comparison. The pin binds the original successful main-push Design
run and attempt, job and artifact IDs, artifact name and ZIP SHA-256, plus SHA-256
of the raw `candidate.json`, original `preview-receipt.json` and native destination
projection bytes. Its schema is `financial-activation-candidate-v1`; its exact
fields are `schema_version`, `repository`, `workflow`, `head_sha`, `run_id`,
`run_attempt`, `job_id`, `artifact_id`, `artifact_name`, `artifact_sha256`,
`candidate_record_sha256`, `projection_sha256` and `preview_receipt_sha256`.
There is no backup boolean or private storage identifier.

After candidate C is independently retained and read back, a control-only commit
C′ adds this pin. Design downloads the exact C artifact, verifies its historical
successful attempt, reconstructs the retained predecessor for the comparison
baseline, and re-tests the same corrected directory with all existing budgets.
It replays the source proof at the original evaluation time and checks expiry at
the actual current time. It never rebuilds or renews the corrected data clocks.
PR runs exercise the same restoration path without publication authority.

The new artifact retains `captured_ui` C and the original preview/projection
bytes. Only `candidate.json`'s `producer` changes to the actual testing run C′;
`captured-candidate.json` retains C's exact original record and
`activation-candidate.json` retains the pin. A pin cannot chain another handoff.
Publication requires C′'s completed exact current-main CI and Design gates,
unchanged protected Git objects, the pinned C attempt and bytes, and the current
source, predecessor and price checks. A missing, changed, expired or superseded
pin fails closed; it cannot select a newly regenerated candidate instead.

Activation rereads the original source and certifier attempts, reproduces the
native projection from original source bytes at its recorded evaluation time,
then checks it at the actual current time. Baseline compiler migration and
financial-only comparisons protect the complete original universe, chart
history, prices, liquidity and other nonfinancial inputs. An unchanged source
receipt inventory cannot authorize another equal-price activation. A changed
predecessor or expired proof invalidates the prepared candidate.

The publisher copies the tested corrected bundle. Only content-addressed audit
assets and its new `publication.json` are added. Two final rechecks verify the
same gated artifact, source, predecessor and complete final inventory. The
ordinary new-UI path remains held while its requested correction is unactivated.

## Future ordinary updates

The activation receipt establishes a stable source lineage: exact source and
certificate identities, original native projection hash, receipt inventory and
policy. Its original projection and target base remain content-addressed assets.
Later advancing exports restore those original bytes from the verified live
publication; expiry of an operational Actions artifact does not reset or erase
the lineage.

Normal preparation first builds the new-price baseline with the already approved
consumer. The distinct `financial-generation-carry-v1` helper evaluates owned
financial evidence against that exact new target at the real build time. Source
capture clocks, receipt bytes and issuer context are retained. New/unverified or
conflicting symbols receive explicit unavailable values; expired evidence stays
unknown. The strict original correction projector's date/price equality is
unchanged. The final carry comparison protects new price bytes and prior daily
history, independently verifies the one allowed first-observation catalog edit,
and rejects missing or replaced active lineage.

Each receipt binds stable source lineage separately from the current evaluation
generation, exact predecessor, new price artifact and manifest, approved UI and
complete data inventory. Current decisions may expire; historical observations
and source capture dates are never rewritten to make them fresh.

Carry grants no chronology exception. The existing newly approved UI path may
reuse the current price date only after its normal exact CI/Design gates; that
build also carries the same source lineage. Re-evaluation alone cannot publish
the same UI and price observations again.

## Activation prerequisite

Before adding the activation pin or publishing, complete the controller's
end-to-end fixtures and the actual coordinated candidate's normal CI/Design/data
gates, and independently
retain and verify the exact final source ZIP, full predecessor ZIP, native/source
projections, preview receipt and tested candidate in durable private storage.
Actions retention remains operational and expiring. Storage IDs/links do not
belong in repository requests, public receipts or CI logs. The control-only pin
commit allows the exact retained bytes to be tested again without changing their
receipt or projection. It does not replace that backup requirement or any normal
gate, and does not allow same-UI/same-price ordinary publication.

## Separately approved one-capture performance exception

The ordinary CI + Design path above is unchanged. The optional, inactive-by-default
[one-capture exception](financial-performance-exception.md) keeps the failed Design
run and original diagnostic truthful and requires separate approval, successful
artifact-only certification, an exact pin, and an explicit release intent.
