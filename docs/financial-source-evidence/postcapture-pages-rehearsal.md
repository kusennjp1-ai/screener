## Executable entrypoints and budget admission

The fixture and supervisor accept `--stage seal`, `--stage publish`, and
`--stage carry`. The latter two also require `--checkpoint EXACT_DIRECTORY`
and `--checkpoint-sha256 EXACT_PRECEDING_JOB_OUTPUT`. There is no arbitrary
command or clock override. The existing default `full` mode remains available
for explicit local diagnostics, but the CI workflow does not use it.

For each stage the workflow first runs closed input retrieval with
`POSTCAPTURE_REHEARSAL_STAGE=seal|publish|carry`, then runs:

```sh
python .github/scripts/run-postcapture-pages-rehearsal.py \
  --stage seal \
  --inputs "$RUNNER_TEMP/postcapture-pages-inputs/inputs.json" \
  --output "$RUNNER_TEMP/postcapture-pages-fixture" \
  --reports "$RUNNER_TEMP/postcapture-pages-supervisor" \
  --node-modules "$GITHUB_WORKSPACE/frontend/node_modules" \
  --python "$RUNNER_TEMP/postcapture-pages-python/bin/python" \
  --job-start "$RUNNER_TEMP/postcapture-pages-job-start" \
  --parent-network-namespace "$parent_namespace"
```

This fixed command must execute inside the workflow's new unshared network
namespace and credential-free environment. Publication/carry add their two
checkpoint arguments. The workflow supplies the corresponding artifact IDs and
manifest hashes through job outputs; it never infers the latest checkpoint or
accepts an arbitrary remote artifact. Input retrieval checks each current job's
own authenticated API start clock and requires the original direct-main parent,
unchanged #99 deployment, closed source branches, artifacts and terminal states.

Every stage retains the **95-minute process / 110-minute job** ceiling, stopping
at job start plus 100 minutes or 95 execution minutes, whichever is earlier.
The ten-minute upload reserve covers checkpoint upload (four minutes), bounded
report collection (one), and report upload (five) in seal/publication. Carry keeps
the original two/eight-minute report reserve. Publisher child caps are 20 minutes
inside the unchanged overall deadline; the measured plan's old 15-minute cap had
only eight seconds remaining. Node/Python memory and storage reservations remain
unchanged. Checkpoint transfer bytes are measured separately from the report
allowlist and are explicitly diagnostic artifacts, never deployment inputs.

The original authenticated job began at 19:50:40 UTC and its supervisor began
at 19:53:52.307 UTC: setup, tests and all five input retrievals/extractions took
**3m12.307s**. Publication's 90-minute admission therefore has about 6m48s of
additional setup capacity relative to that observation. Downloading the new
checkpoint is additional and not yet measured; a download/setup overrun fails
before starting another expensive stage. Step timeout maxima are independent
ceilings, not promises that their worst-case sum can be admitted.

Seal admission requires at least 75 remaining execution minutes. Publication
requires at least 90: its five independent full-verification passes at the measured
plan cost project **74m19.560s**, leaving at least **15m40.440s** for restore,
packing, guard/byte proofs and checkpoint retention. Those additional durations
remain estimates, not a demonstrated full-cohort pass. A slower replay fails the
bound while preserving its earlier checkpoint. Ordinary carry is separate because
including it in that budget would be too tight. It requires at least 30 remaining
minutes and can use up to the same 95-minute cap; its full-cohort duration remains
unmeasured. No threshold asserts that a stage is guaranteed to finish.

The workflow retains both complete targets and comparison diagnostics in bounded
reports, plus the explicit checkpoint manifests. A later stage begins only after
the previous job uploaded its exact checkpoint successfully. A failure in
publication or carry therefore does not require replaying the original sealed
prefix to investigate the same bytes. A full rerun remains a new experiment and
must not silently replace a retained checkpoint. No long run is launched by this
local preparation.
